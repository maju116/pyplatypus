[0.8.0a54] - 2026-10-29

Documentation only, and the pair rather than the prose is the reason it is a release. The configuration guide gains Predicting on images you have no labels for, which is the other half of maju116/rplatypus#246 - the guide is one document in two repositories and both sides carry the same sections, so a subsection written on one side alone is the drift §3F of the workbench’s notes is a list of.

The R half: done already, and that is why this release exists at all. 0.8.0a52 shipped the capability and deliberately did not document it here, because written on the engine’s side alone it would have described, in the shared guide, something an R reader could not do until the pin moved. The pin moved in rplatypus#246, so this half is now writable - which makes the ordering the point rather than an accident: the guide’s two halves are written in the order the capability becomes true, not in the order the code lands.

Dated 2026-10-29 while the work and the pull request are 2026-10-28’s, which is the first entry here to straddle a day. Both places were corrected rather than left: the heading and CITATION.cff’s date-released are the release’s, matching the tag, as a51 through a53 all do.

And this is the one case test_the_citation_carries_the_date_the_changelog_gives_that_version says out loud that it cannot catch. That test holds date-released to the changelog heading rather than to a clock, and its own docstring states the limit: “It cannot catch both being wrong together, which is the limit worth stating rather than papering over with date.today() - that would fail every time the suite is run on a day that is not release day.” Both were 2026-10-28 and agreed with each other, so the suite was green on a release that would have been a day early in the one field a citation is for. The limit is still the right trade - a clock in that test breaks every ordinary run - and what closes it is the release loop reading the date when the tag is cut, which is what happened here.

A release with no code in it, which has two precedents here. 0.7.0a3 was documentation only and 0.8.0a9 a README section on this package’s own page. The wheel is behaviourally identical to a53’s; what reaches a reader arrives through the docs job on merge rather than through PyPI, and the version exists so that the entry below has somewhere to live.

Changed

  • guide.qmd gains ### Predicting on images you have no labels for, under One label instead of a mask, with a validated YAML block and the three refusals named: predict() and predict_labels() work, evaluate() refuses by name, and balance() refuses for the same reason. It says what the truth column carries - label: None, and labels: None rather than [], because an empty list there means this image carries none of the findings - and it names the one layout that cannot express an unlabelled split at all, since nested_dirs makes the directory the label.

    A ### rather than a ## is deliberate and measured: both suites pin only ^## (.+)$, so a subsection needs no merge ordering between the two repositories and the pair’s own test has nothing to say about it. The ## sections are unchanged on both sides.

    And a documentation-only release moved the test count, which is worth knowing before anybody reads that as a contradiction. The suite went 2686 to 2691 with no test written, because the guide’s tests are parametrised over the guide’s own content: collected before and after, the YAML block added two cases, two existing blocks were renumbered - the parameter ids carry line numbers, so inserting prose above a block renames its test - and three names this subsection offers a reader are each checked to resolve: answers, balance and predict_labels, none of which any guide prose had named before. All three resolve. So the prose added here is held to this package’s surface by the same instrument spec_schema()’s descriptions are, which is the strongest reason to write a guide section as prose naming functions rather than as description.

[0.8.0a53] - 2026-10-28

A method that asks what the model said was handed the loader built for optimising over. maju116/pyplatypus#321.

The R half: none beyond the pin - and that is not R needs nothing. This is a defect an R user meets, through predict(fit, split = "train") and evaluate(fit, "train"), and the fix reaches them by the pin moving and by nothing else. §1 records 0.8.0a47 and a48 as the two releases that taught this distinction, and §3E read literally would say to leave the pin alone on all three. The pin is moving anyway for maju116/rplatypus#245, so one move carries both - the ratchet rather than two R releases.

Fixed

  • predict(split="train") came back in the training loader’s shuffled order, so answers() paired every key with another image’s probabilities. loader() derived both shuffle and drop_last from split == "train", which is right for the pass that optimises and wrong for every method that asks a question - and predict’s own docstring promises “in the split’s own order”.

    Measured: two predict(split="train") calls on one split are a permutation of each other - the same multiset of rows, not one row in place - and at 16 samples with batch_size: 8 nothing is dropped, so no count disagreed and nothing refused. answers() then reported label == predicted on 8 of 16 training images, which is chance on two classes.

    drop_last is the same defect reading as a score rather than as rows: evaluate("train") scored only the images that fit a whole batch and reported the number as that split’s, and answers("train") on a ragged count ended in ValueError: zip() argument 2 is shorter three layers from the cause.

    Both flags are the caller’s now, defaulting to ordered and complete, and fit is the only caller that asks for either. That is not a new parameter: the three other engines already take shuffle from the caller and every asking site in them passes False, so this is one question answered four times with the odd one out being the bug - the same shape _has_any_labels had in 0.8.0a52, one release earlier.

    The two flags stay separate rather than travelling under one name, measured rather than tidy: drop_last was independent of data.shuffle, so keying it to shuffling would stop dropping the ragged last batch for anybody running shuffle: false - and a last batch of one is a batch-norm with nothing to normalise over, which is the whole reason the flag exists here. The len(base) > batch_size guard stays inside loader(): a split smaller than one batch would otherwise be emptied by the flag fit always passes.

Changed

  • The test that pinned the old behaviour was named for two properties and asserted one. test_the_loader_shuffles_training_only_and_drops_a_lone_last_batch checked drop_last and said nothing about shuffling, which is why predict could come back in it. It is replaced by one that asserts the asking defaults, the capability fit asks for, and the inner guard at its boundary - eight samples against a batch of eight, where dropping would leave nothing.

    And moving a decision to a caller needs the caller pinned: a mutation making fit pass shuffle=False left all 29 other tests in this file green. Training a classifier on batches that are each one class is a real degradation and no number in this suite would have moved. So fit’s own request is recorded off loader and asserted, with shuffle: false in the data block as the control that the value is read from the specification rather than hard-coded. Five mutations, five caught.

[0.8.0a52] - 2026-10-28

The one task whose whole output is a label per image was the only one that could not predict on unlabelled images. maju116/pyplatypus#320.

The R half: one thing, owed rather than built - maju116/rplatypus#245. On the single-label route R is already right: predict()’s comment says “label is NA on a split that carries no labelling, which is what a test set often is”, and measured against rows_to_frame, a None from the engine does come back as NA. That sentence described a state R could not reach until this release, and it is true now rather than aspirational. The long form a set of labels comes back in is the half that is wrong: label is classes %in% as.character(unlist(row$labels)), which for nobody said is FALSE FALSE FALSE - the same three rows a film carrying none of the findings produces. The comment directly above it claims long form is “the only shape in which ‘this image has none of the findings’ is four rows of FALSE rather than an empty cell that could also mean unread”, so the property that prose rests on is the one that stops holding here. The pin moves with that fix, because R cannot reach this state against an older engine.

Fixed

  • A classification test set of images alone was refused, where every other task in this package accepts one. ClassificationEngine._has_any_labels() returned True unconditionally while its own docstring described the distinction it was not making - “in nested_dirs mode the label is the directory … a CSV may name no label column at all” - so _discover_test’s fallback was unreachable and a key, images CSV as test_path died in the labelled read. Three legs, measured: the labelled read refuses with needs a 'label' column; the same file read only_images=True is accepted at four samples; and _has_any_labels() answering True is the only reason leg 2 was never reached. The reader could already do it and nothing asked.

    It answers now: True in nested_dirs mode, because the directory is the label and there is no unlabelled form of that layout to fall back to; otherwise whether the test CSV’s header names the column a label would be read from. For a set of labels that is labels_from’s columns rather than label, and the answer is whether the header names any of them - _discover_test is built on none and some being different things, so a file naming two of three classes still refuses by naming the third instead of quietly becoming an unlabelled split and reporting nothing about the two that are there.

  • Two guards that could not fire became reachable, and both were wrong in the state they had never been in. This is the honest cost of the fix rather than scope: #320 is closed by one method, and making a state reachable is what obliges the code that meets it.

    balance() on an unlabelled split counted it anyway and reported every class at zero, with never listing all of them and labels_are_a_set reading False whatever the specification said - three readings that look like findings about a dataset and are findings about there being no labels. §4’s a zero in a table is read as a result. It refuses by name now, in its own sentence rather than _needs_labels’s: that one says there is nothing to score against and is about asking a model for a number, and this is a question about the data with no model in it.

    answers() reported labels: [] for an image nobody had labelled, which is exactly how it reports an image carrying none of the findings - a labelled row, and the commonest one in every dataset this reads, as the reader’s own comment says. None now, which is the marker the reader already uses and what the single-label branch has always said.

Changed

  • One reader for the header question, and the claim that said there could not be one was false. labels_in_test_split’s docstring said detection “answers this differently and must not be changed on the way past”; detection’s own _has_any_labels was that function’s body verbatim, modulo one return False folded into splitting an empty string. What differs between the tasks is label_column and subdirs, both derived per task, which is what lets one function serve all of them - and classification would have been a fourth copy. All four engines call it now, columns says which CSV columns to ask about, and the one genuine difference is classification’s and happens before the call.

    Measured rather than asserted, by mutating each branch and running each task’s suite separately - and the table is the finding, not the convergence:

    nested-dirs branch -> always labelled   CAUGHT by detection, segmentation
                                        uncaught by instance, classification
CSV branch -> never labelled            CAUGHT by classification only

    So detection does depend on the shared function, which is what the convergence needed to show. And the CSV half of this question had no test in any suite before this release: the two tasks that read a CSV test split never exercise it, so detection’s own copy of that branch was untested code for its whole life. The tests added here are the first.

  • tests/test_engine_base.py’s structural columns are four - classification arrived in 0.8.0a49 and that file never grew a column for it, and the question it would have been asked there is the one whose answer was return True. Its behavioural columns are still three and are recorded in the file as owed: they need a built engine with its own layout and a _needs_* wrapper this engine does not have.

  • No guide section, which is a decision rather than an omission. Neither guide says a test split must be labelled for any task, so §3C’s a change to how a run is written is not triggered - nothing about the configuration format changed, a CSV simply has one column fewer. The subsection worth writing is predicting on a folder of images you have no labels for, and it belongs on both sides at once; written here alone it would document, in the shared guide, a capability an R reader cannot use until the pin moves. So it is a task on maju116/rplatypus#245 rather than a section here.

  • One defect found while writing these tests and filed rather than fixed - maju116/pyplatypus#321. The control for an unlabelled split needed a labelled one beside it, and answers(split="train") was the obvious place to get it: it comes back in the training loader’s shuffled order, so each key is paired with another image’s probabilities. Two predict("train") calls on one split are a permutation of each other, and at 16 samples with batch_size: 8 nothing is dropped, so nothing refuses. It has nothing to do with labels being absent, so it is not repaired here - the test’s control reads the validation split instead, and says why.

[0.8.0a51] - 2026-10-28

Two defects found by reading the task that had just shipped, and one new instrument. maju116/pyplatypus#316 and #312.

The R half: none, and the pin does not have to move for it - which is a stronger claim than None beyond the pin, and the distinction is one 0.8.0a47 and a48 are recorded here for not having: those two were defects whose fix reached an R user by the pin moving and by nothing else. Neither of these does. write_splits is not exported from R, and classification_data() refuses a split_dataset() by name before any interpreter starts, so the branch repaired below is unreachable from that side; and ?detection_crops already documented all seven keys correctly - see the second item.

Fixed

  • write_splits() wrote sample.masks whatever the task, so a classification split written to CSV lost its labelling entirely: the label column was renamed and its cells were the masks a classification sample does not have. Measured on 6 images in two classes - six empty cells - and the file then refused at the reader, one run later, with no label name on every row and yielded no usable samples. That message is a sentence about the dataset, so the first place anybody looks is the data, and the data is fine.

    What the label column holds is read off the samples now, the way stratified_split already dispatches: one masks column of paths, one label column of names, or one column per class holding 0 or 1. Samples that disagree are refused - one CSV has one header.

    A set of labels takes classes, and is refused without them rather than taking the union of what the split happens to carry: a class no image in that part has would simply have no column, and the file would then describe a narrower problem than the one being studied. Same argument and same parameter name as save_class_masks.

    label_column now defaults to None, which takes the name from what the samples carry. The mask layout is byte-for-byte what it was, and a test asserts that rather than trusting it.

    The test that would have caught it already existed and was written over masks. test_written_csvs_are_readable_by_the_config_file_mode writes a split and reads it back, which is exactly the right shape, for the one label kind the writer handled. The round trip is now asserted for a name and for a set as well - and asserted as a round trip, because a test demanding a non-empty cell passes on a writer that puts the key there.

A detection epoch is pooled by what the loss divided by. maju116/rplatypus#218.

Fixed

  • DetectionTrainer._run_epoch ended in {key: value / batches}, and the thing being averaged is not an average over examples. Every component of the YOLO loss is divided inside the loss: coordinates, objectness and classes by a grid’s object count, and no_object by the cells it supervises. Averaging those over batches weights a frame holding thirty blood cells the same as a frame holding two.

    This is not 0.8.0a40’s repair in another trainer, which is why it is its own release. There the per-batch value was already a mean over the batch’s examples, so weighting by batch_size turned a mean of means into the mean - one correct answer. Here the denominators live inside the loss and there are four of them per scale, so LossParts carries grids, one GridParts per scale holding the four terms and the two divisors, and an epoch is sum over grids of (sum over batches of value * divisor) / (sum over batches of divisor).

    The grids are summed, not mixed. forward sums the three scales, each already divided by its own grid’s count, so pooling across grids and batches together would turn a sum of three into an average of three. That is a different quantity rather than a different weighting: it moves the reported loss by a factor of about three and picks epochs for that reason. The first measurement of this issue made exactly that mistake and reported a moved epoch that was the artefact.

    total is rebuilt rather than pooled, because it is a weighted sum of four terms divided by two different denominators and so has no denominator of its own.

Migration

  • A detection run’s epoch line changes. On BCCD at the example’s own settings the reported val_loss moves by up to 0.33 over 150 epochs, and the change is not a constant offset - it ranges from -0.14 to +0.33 and changes sign. Anything comparing a recorded detection loss against a new run is comparing two definitions.

  • No published number moves. bccd-yolo3’s card reports average precision through evaluate_classes and evaluate_images, which score per image on their own path. What changes is which epoch early_stopping keeps.

  • Measured, and it did not move the epoch on the run that matters. 150 instrumented epochs of examples/detect_blood_cells.py: both poolings pick epoch 14 and agree on the first five in order. That is reported as too close to call rather than as no effect - the winner’s margin over the runner-up is 0.0558 and the gap between the two poolings varies across that neighbourhood by 0.0585, which is 1.05x the margin. [0.8.0a26] - 2026-10-15

Two of the four issues in the “Losses and metrics” milestone, and the other two are answered rather than built - both of them were filed with the measurement that says not to. maju116/rplatypus#113 and #114.

Added

  • surface_dice, a metric: how much of each boundary lies within a tolerance of the other. rplatypus#113. The third question this package can ask of a mask, after volume (dice) and connectedness (cldice): how far wrong is the edge. The volume vignette ended on a model at Dice 0.88 whose volumes were 12% to 23% too large, and this is the number that says so directly rather than being inferred from two columns that disagree - and it is what boundary optimises while nothing here reported it, so that loss was being judged by the metric it exists to improve on.

    Normalised surface Dice as published (Nikolov et al., 2018), symmetric: the truth’s surface near the prediction is the boundary’s recall, the prediction’s near the truth is its precision, and one ratio weights them by surface size.

    tau is required and has no default, because a tolerance belongs to the structure and the dataset - conventionally the inter-observer variability for that structure. It is in millimetres when target_spacing puts the samples on a common grid and in voxels when it does not, which is the same pair of answers the signed distance map gives and for the same reason. The only metric here that reads the spacing, which is why it belongs in a package that carries one: a 0.5 mm and a 2.5 mm acquisition are not comparable in voxels at all. The spacing reaches it the way multilabel reaches the others - the builder joins the spec’s tolerance to the data’s voxel - and InstanceData has no target_spacing field, so an instance run measures in voxels and says so.

    Written as a dilation rather than a distance transform, and measured. A voxel is within tau of a surface exactly when a ball of radius tau centred on it contains a surface voxel, so the question is a morphological dilation by that ball - which costs the ball’s volume per voxel where a transform costs the whole image whatever tau is:

     256x256, batch 8, two channels     2.7 ms on the GPU      41 ms on the processor
 128^3,            two channels    23.8 ms on the GPU     372 ms on the processor
 the same by scipy's transform                            948 ms on the processor

    #113 worried that a distance transform at 128^3 costs 710 ms, which is the whole epoch budget; this is thirty times less and can therefore run every batch. Verified against scipy.ndimage.distance_transform_edt - a different algorithm, so agreement is evidence rather than a shared bug - exactly at four tolerances over isotropic and anisotropic spacings at both ranks, and the whole metric against a scipy-only implementation to 1e-6 over thirty pairs.

    include_background defaults to False here, and for a measured reason rather than the usual one: the background’s boundary is the foreground’s boundary plus the edge of the picture, and that edge agrees between any two masks whatever the model did. Measured on four random pairs at tau 2, background 0.6110-0.7030 against foreground 0.5583-0.6266 - higher every time. That is agreement on the field of view. For the same reason a mask running off the edge has no surface there, which also makes two solid masks score 1.0 rather than 0/0.

  • generalized_dice, a loss: classes weighted by the inverse square of their volume. rplatypus#114, in both loss and boundary’s region.

    The usual argument for it does not hold in this package and the help page says so. Generalized Dice is introduced as a fix for Dice being dominated by the background; dice here is a mean over the class channels, so a lesion in 1% of a frame already carries the same weight as the 99% around it. Measured on a 1% target with two predictions - one finding the lesion and leaking a false positive of equal size, one missing it entirely and getting the background perfect:

     dice               0.1658 finding   0.4731 missing   prefers finding by 0.3073
 cce                0.1600 finding   0.1600 missing   indifferent
 cce_dice           0.1629 finding   0.3166 missing   prefers finding by 0.1536
 generalized_dice   0.3278 finding   0.9511 missing   prefers finding by 0.6233

    So what it adds is weight beyond an equal share - 1 to 9801 on that target rather than 1 to 1, and twice the margin between finding the lesion and missing it. And the objective that is genuinely dominated is the per-pixel half of cce_dice: to cce a false positive and a missed lesion of the same size are the same number of wrong pixels, which is the indifference in that table. The claim in the issue was inherited from the literature and is wrong about this implementation; it is corrected rather than copied, and the table is held by a test.

    Two decisions, both in the docstring and both tested. An absent class has no volume and so an infinite weight; it is given the largest finite weight in its sample, as the published implementations do, so inventing a class that is not in the picture costs as much as missing the rarest class that is - weight zero would make it free. A sample with nothing present at all has no finite weight to borrow, so its weights are flat and it is scored exactly as dice scores it; without that fallback every empty-truth sample reads a perfect 1.0 and a model predicting a lesion on a clean frame is never told.

    And the weights are rescaled to a mean of one, which the published quantity is invariant to and which is what makes smooth mean here what it means everywhere else: unscaled, the weights are of order 1/volume^2, so a smooth of 1.0 is not a small regulariser but the whole numerator. The control caught it - with three equal classes the coefficient read 0.855 where pooled Dice reads 0.355. Added

  • mse, l1 and smooth_l1, and the question they exist to force: where is the target defined? (#209) A continuous instance target - a flow field, or horizontal and vertical distances - is defined on the objects and undefined off them, so a builder writes zero on the background. Measured on the 536 Data Science Bowl cases: the foreground is 13.97% of the pixels at 256x256 (13.48% at native size, 0.03% to 59.2% per case, 167 cases under 5%), so an unmasked mean spends 86% of the objective on a value a single output bias satisfies exactly.

    So where: is a field rather than a convention. foreground divides by the mask’s own total, which makes the number mean average error per object voxel; everywhere is the other defensible answer and is what CellPose and HoVer-Net’s plain regression terms do - their background zero is a real value rather than a missing one. foreground is the default because it is the reading whose number means something, and because the trap is otherwise on by default.

Decided

  • A vector target is rebuilt from the augmented label map, never corrected (#210). Two measurements, both in tests/data/test_vector_targets.py where a library bump re-runs them:

    • albumentations 2.0.8 never invents a label value. Sixteen transforms, twenty seeded draws each, a label map of forty distinct ids: not one output value was absent from the input, and the control is that the same transform with the map sent down the image path invents hundreds. So an instance label map travels through the augmenter unharmed and the target can be built from what comes back.
    • A crop moves an object’s centre, and no correction can answer that. Negating x after a horizontal flip is exact - 0.0% of foreground voxels disagree with a field rebuilt from the flipped labels, at 0.0 degrees, against a median of 90 and a maximum of 167.3 if the negation is left out. After a 32-pixel crop 49.5% disagree, by a median of 8.9 degrees and up to 180, and there is no component to negate: the surviving part of an object has a new centre, so the arrows carried in point at a place that is no longer in the picture.

    Rebuilding is therefore correct by construction for every transform rather than for an admissible list of them, which also retires the idea of refusing transforms by name. It covers tiling for free - a tile is a crop, it happens before augmentation, and a 2048-pixel retina cut into sixteen would otherwise carry sixteen fields built for the whole picture.

    The data path already had the right shape and the wrong array in it: masks are augmented as class indices and one-hotted afterwards, which is exactly the route, but _to_classes throws instance identity away first. So #212 carries the instance label map into the dataset rather than deriving a target offline, and a test pins that ordering instead of a docstring claiming it.

  • AlbumentationsAugmenter refuses a floating-point mask, which is what keeps that decision from being quietly undone. A flow field sent through as a mask comes back the right shape, the right dtype and the right range with its arrows pointing the wrong way; the loss falls, the model trains, and nothing downstream can tell. Every path in this package sends an integer - labels_to_classes, colours_to_classes and labels_to_regions all return int64 - so the guard costs nothing it should not.

  • Instance separation, and the measurement that says it is worth training (#159). The proposal was a semantic mask plus a separation signal; of the two signals on the table this takes the boundary, because it turns the problem into three mutually exclusive classes - background, object interior, object rim - which is ordinary semantic segmentation on the softmax path this package already has. Nothing new in the model, the loss or the metrics.

    parts_from_instances() decomposes an instance label map into those parts and instances_from_parts() grows them back: the interiors become seeds and every other foreground pixel joins the nearest seed, which distance_transform_edt(return_indices= True) answers in one call. No new dependency - scikit-image is not here and is not worth adding for one function.

    No model is trained, and that is the point of this release. The post-process is what caps the approach, and a cap can be measured without the thing it caps: feed the ground truth through it and score the result against the same ground truth. On the exact 134 cases dsbowl-unet’s card reports:

     interior and rim, grown back        0.9846    median 1.0000
 connected components                0.7655
 the published weights, as measured   0.4888    (0.8.0a13)

    Three readings, and the middle one is new. Connected components caps any model at 0.7655 on this data - a perfect semantic mask still scores that, because touching nuclei are one region. So the published weights’ 0.4888 is not one failure but two: 0.4888 to 0.7655 is the mask’s own error, and 0.7655 to 0.9846 is what separation can buy and no better mask ever will. examples/separation_ceiling.py is the script, it trains nothing, and it prints both ceilings from one run over one set of pictures.

    What the decomposition costs, counted rather than assumed, over those 134 cases: the plain erosion would have erased 6 objects in 4 cases - a nucleus one or two pixels wide has no interior - and an interior falling into two pieces gained 52 objects in 20 cases, which is most of the 0.0154 the ceiling sits below 1.0.

    The erased objects are handled rather than ignored, because an object absent from the target is an object the model is told not to find: a false negative in every epoch and in the score, with nothing to say the target was at fault. An object whose interior comes back empty falls back to an erosion that only removes pixels touching a different object, and one still empty after that keeps itself whole.

Fixed

  • The weak erosion could not see the objects it was protecting against. It was handed a label map with every other object masked out, so a pixel touching a neighbour read background there - and background counts as agreement in that pass by design. The thin object was kept whole and handed a seed it shared with its neighbour, which is the one outcome that fallback exists to prevent. Found by a test, not by reading, and the ceiling above was re-measured afterwards: it had been 0.9853 with the defect, which is wrong in the third decimal and was nearly published.

Notes

  • Nothing in pyplatypus.instances is in pyplatypus.__all__, deliberately: the top-level namespace is paired with R’s reference groups and the shared order is held by tests on both sides. These names live on pyplatypus.instances until R has something to say about them.

For the R package

  • Nothing, and the pin should not move for this. No R surface reaches the instance post-process yet; platypus#103 is the R half of the whole milestone and it waits on #160, the spec tag, which is what will make any of this reachable from a configuration.

[0.8.0a14] - 2026-10-12

Added

  • regions: overlapping classes, named as unions of a label map’s values. The first half of multilabel segmentation (#91), and the decision in front of it was the author’s: nested regions first, one binary file per class deferred.

    The case is BraTS and the lesion-inside-an-organ family - liver and tumour, kidney and cyst, lung and nodule. The ground truth gives every voxel one of {0, 1, 2, 4} and the three scored classes are unions of those values:

     regions:
   - name: enhancing
     of: [4]
   - name: core
     of: [1, 4]
   - name: whole
     of: [1, 2, 4]

    So the overlap is a convention applied to exclusive data, not a different file format, and nothing new is read off disk. regions is a third way of naming classes rather than an addition to labels: a region is a membership test, so the complete vocabulary of values never has to be declared. Exactly one of colormap, labels and regions is given, and - as with detection’s classes, for the same reason - regions have no background entry, because each channel is an independent binary question.

    Why nested first was the cheaper half as well as the one the data wanted. One integer per voxel survives tiling and augmentation, both of which operate on a single-channel array today, so neither had to learn anything. The expansion to channels stays in the last step before the loss, where classes_to_onehot already was:

     exclusive    onehot = np.eye(n_class)[classes]
 overlapping  onehot = table[classes]      table[v] = the regions value v belongs to

    Same indexing; np.eye is the special case where the table is the identity. The one difference that matters is row 0, which is zeros rather than a class. labels_to_classes sends an unmatched voxel to index 0 because index 0 is a class there - the background a colormap puts first - so reusing it unchanged would have made background a member of whichever region holds the lowest value. On BraTS that is 1, which is in both core and whole, so every background voxel would have been in two of the three regions and the model would have trained on it without complaint.

  • Per-channel objectives, and the four places mutual exclusivity was hiding. probabilities gained a multilabel argument and is the single home of the softmax-or-sigmoid decision; every overlap-based loss reads it through SegmentationLoss.probabilities rather than calling the functional form, so Dice, IoU, Tversky, focal Tversky, combo and the surface term all moved with one line. cce and focal gained binary forms, metrics threshold each channel instead of taking an argmax, and predict returns a stack whose channels do not sum to one.

    binary_focal agrees with torchvision.ops.sigmoid_focal_loss to within float32’s resolution over five (gamma, alpha) settings, and reduces exactly to binary_cross_entropy at gamma=0 - a control the implementation could not satisfy by accident. Both are in the suite, and the torchvision numbers are baked in rather than imported because torchvision arrives only with the encoders extra.

    No tighter number than that is pinned, because there is not one to pin: these are float32 reductions over 384 elements, so the last digit belongs to the order the hardware adds them in. macOS on ARM and Linux on x86 disagree by 8.6e-08 relative, under float32’s eps of 1.19e-07, and a first version of the test asserting 2e-08 absolute turned one macOS job red while being right about the arithmetic. The bound that replaced it is rel=1e-6, chosen against both ends: twelve times the platform noise, and five orders of magnitude under the 55% to 67% that the mutation this test exists to catch actually moves the numbers by.

    The reduction differs from the categorical form and that is deliberate. Categorical cross-entropy sums over channels, which picks out the one true class of a one-hot target. Here every channel contributes, so a sum would make the loss grow with the number of regions: three regions would read three times the scale of one, and cce_weight in a blended loss would mean something different on every dataset. The mean keeps one voxel worth the same whatever it was asked. label_smoothing divides by two rather than by n_class for the same reason - each channel is a two-outcome question.

  • A metric now reports what the model was asked. With an argmax, a voxel correctly predicted in both the core and the whole tumour was credited to whichever channel read higher and scored as a miss in the other. On the smallest case that can show it - one voxel, in two regions, both predicted - Dice went from 0.833 to 1.000.

Changed

  • inspect_masks reports regions by name, and unmatched means something different there. missing_classes keeps its meaning exactly and gains the failure regions invites: of: [3] against data holding 4 is a channel of zeros, which trains to predict nothing and scores a Dice of 0 while every other number looks ordinary. It is refused before training with the region named. unmatched, on the other hand, counts background - which is deliberately not a region - so it sits near 1 on any dataset where the thing being found is small. On BraTS that is the correct answer and it looks like the catastrophic one, so the warning that reads it is suppressed for regions rather than left to cry wolf on every correct run.

  • The class fingerprint written into every run record and weights sidecar now names the regions. n_class alone cannot tell three exclusive classes from three overlapping ones, and weights from one must not be read back as the other.

Refused rather than served

  • lovasz with regions. Lovasz-Softmax sorts the errors of a softmax over mutually exclusive classes; the independent form is the Lovasz-Hinge, a different construction rather than a setting on this one. Run as it stands on sigmoid channels it would return a number and a gradient, which is the worst available outcome. The property lives on the loss specification (supports_multilabel), so the refusal arrives at load time and pyplatypus.objectives.losses reads it rather than keeping a second list.

  • include_background: false with regions, but only when it was written down. There is no background entry, so channel 0 is the first region somebody asked for and dropping it would drop a class. cldice defaults the flag to False and a default is not a request, so with regions the setting is ignored rather than honoured - model_fields_set tells those apart, the same way channels_match_the_data already does for channels.

  • A colour map holding an overlap. onehot_to_colours refuses an array where some voxel is confidently in two classes instead of taking the argmax and writing one of them, which would have produced a plausible picture of something else. Detected from the array rather than from a flag, so a caller holding only a prediction can answer it; a softmax output never trips it, because its channels sum to one.

Not done, so it is not looked for

  • classes_from - one binary file per class - is the only shape that can express genuinely independent overlap, a vessel crossing an organ or two annotators’ masks. Deferred, not dropped: #91 stays open for it and unite_masks’s element-wise maximum is still where per-file identity is destroyed.
  • Drawing a multilabel prediction. What one picture of three overlapping regions should look like is a real question with no answer yet, and half of one would be worse than none. onehot_to_colours refuses rather than guessing, which is the honest state until it is designed.
  • A guide section. The guide’s section list is pinned and paired with the R package’s (“change both or neither”), so a narrative section on regions lands with the R half rather than documenting in R something R cannot do. The field’s own description is on the generated configuration reference now, which is where a reader meets it.

For the R package

  • Nothing moves yet, and the pin should not. regions is reachable from R the moment the pin moves, because R forwards the data block it is given - but available_weights()-style free inheritance is not what this is: the R surface documents its fields by hand, so regions needs roxygen prose of its own, and save_masks() needs the refusal the author chose for an overlapping prediction. Both are the R half’s work, filed as its own issue.
  • The field-prose ledger will fire, and that is the mechanism working: regions and Region.of are new descriptions R has never been written against.

[0.8.0a13] - 2026-10-12

Added

  • pyplatypus.instances: the Data Science Bowl’s own metric, and the number the published weights score under it. First piece of instance segmentation, and it deliberately builds no model. Detection worked here because it was built metrics-first - every piece checked against something outside itself - and a model chosen before there is a way to score it is a model chosen on nothing.

    The baseline, measured on the exact 134 cases dsbowl-unet’s card reports:

     Dice, on the model's grid                   0.9205
 instance average precision, source grid     0.4888

    The card for those weights says semantic, not instance, and that caveat has been true and unmeasured since they were published. Touching nuclei come back as one region; connected components found 4658 objects where the data holds 5774, and every nucleus a merged region swallows costs twice - a false negative, and a false positive through the region that swallowed it.

    The split is reproduced rather than assumed, and the Dice is the control that proves it. The 134 directories sitting in stage1_validation on the machine this was measured on are a different 134 from the card’s - the card’s worst case is not among them - so scoring those and quoting the published Dice beside it would have compared two different sets of images. split_dataset with the card’s fractions and seed rebuilds the right ones, and the script refuses to report anything unless Dice comes back as the sidecar’s 0.9205236150257623 to seven decimals. That mistake has a history on this dataset: a directory of 134 images and a card measuring 134 held-out images were taken for the same 134 once before.

    What is in the module:

    • label_map() and read_instances() - the per-object files read as instances instead of united into one mask. unite_masks() takes the element-wise maximum, which is where instance identity is thrown away at read time; nothing new had to be collected.
    • iou_matrix() - pairwise IoU from a contingency table rather than pair by pair, because one image in this dataset holds 375 objects and the pairwise form is 140,000 full-image comparisons. Checked against pycocotools to 1e-12 on three seeded problems, then baked in, so the suite needs no dependency - the arrangement the detection metrics already have with that library.
    • average_precision() - the challenge’s TP / (TP + FP + FN) at ten thresholds from 0.5 to 0.95, averaged. Not a precision-recall curve and nothing interpolated, because nothing is ranked: an instance post-process produces regions, not scored proposals.
    • instances_from_mask() - connected components, 4-connectivity, untuned. A yardstick, not a contribution, and a baseline that has been tuned is no longer what later work is compared against.
    • summarise_instances() - the mean over images, which is what the challenge ranked on, and the pooled number beside it. This dataset holds images of 2 objects and images of 375, so the two differ and reporting one alone is how it gets quoted as the other.

    Thresholds below 0.5 are refused, and the strictness of the comparison is load-bearing. Above 0.5 a prediction can satisfy at most one object - two disjoint regions cannot each cover more than half of the same third region - so counting matches is exact and needs no assignment algorithm. The comparison is iou > threshold, not >=: with >=, two predictions each covering exactly half of one object would both count, and the test that catches this is the one where a merged region scores two true positives instead of none.

    Overlapping truth is refused rather than resolved. A mask layer that holds more than one thing per pixel is open work - pyplatypus#158 with pyplatypus#91 - and a metric that quietly took the topmost label would answer that question wrongly rather than decline it.

    Closes pyplatypus#157.

For the R package

Nothing, and the pin stays where it is. These names live under pyplatypus.instances rather than in __all__, so they are not on the reference page and R cannot reach them: instance segmentation becomes a configuration people write when task: instance_segmentation lands (pyplatypus#160), and that is the release where the reference groups and R’s shared order move together. platypus#103 is the R issue and it says the same thing.

[0.8.0a11] - 2026-10-11

Added

  • deterministic, the opt-in that makes a seed mean something on a card. seed has said where it stops since 0.8.0a8: measured on a GTX 1070, two runs of one configuration at one seed agreed to twelve decimals on the processor and differed in the fourth after a single epoch on CUDA, because cuDNN picks algorithms nothing constrained. This constrains them - torch.use_deterministic_algorithms(True), cudnn.deterministic, and cudnn.benchmark off, which is the one that was choosing per shape.

    An opt-in rather than the default, because the cost arrives at a time nothing else here does. Some convolutions become much slower, and an operation with no deterministic implementation raises when it is reached, so a run can stop ten minutes in. Every other refusal in this package happens before anything is read, and this one cannot: whether an operation has a deterministic algorithm is a fact about the installed torch and the device, not about the configuration. The field says so.

    It needs seed, and asking without one is refused. Constraining the algorithms while the initialisation, the shuffle and the augmentation all still vary leaves the run exactly as unrepeatable as before and only slower - half a promise, which is what platypus#122 was filed about in the first place.

    It also sets CUBLAS_WORKSPACE_CONFIG to :4096:8 when nothing else has: from CUDA 10.2 on, cuBLAS needs it or torch raises, and the variable is read when CUDA initialises - which is why this happens in the engine’s constructor and not in fit(). An existing value is somebody’s deliberate choice and is left alone.

    What is tested is that the flag reaches torch, that nothing is asked of torch when nobody asked, that the variable is set without trampling one, that the specification refuses the half-promise, and that an ordinary run still trains with it on. What the field is for - two CUDA runs agreeing - needs a card, and CI has none; tests/test_seeding.py says the same about the other half rather than asserting something it cannot see.

    Closes platypus#122, whose documentation half shipped in 0.8.0a8.

  • save_spec(), the way back out of a specification. from_yaml() read a configuration and nothing wrote one, so the two interfaces were one pipeline and a half: an example could write the YAML of the run it had just done only by keeping the raw dict it started from. Now a specification built in code - or in R, where the bridge already drops unset arguments - becomes a file somebody else can run.

    It writes what was set, not what the object holds, and that is the whole design. On a two-field model to_dict() returns 29 fields, and the difference is not verbosity: a model given weights and no architecture adopts the architecture from the weights sidecar, and the adoption fires on architecture not being in model_fields_set. Dump the defaults and the reloaded specification has all 29 set, so a file that looks like the original quietly stops doing what the original did. defaults=True is the opposite want, kept as a second mode: freeze this run exactly as it resolved, at the cost of it adopting nothing ever again.

    Two things only the round trip could have found, both now tests:

    Every discriminator has to be written even when unset. task is the obvious one. DiceLoss(smooth=0.5) is the one that is easy to miss: name is a Literal with a default, so a dump of what was set gives loss: {smooth: 0.5} - a block with no tag, which comes back as Unable to extract tag using discriminator ‘name’.

    And “annotated Literal” is the wrong rule for finding those tags. It also catches box_loss and annotation_format, which are choices a user makes, and writing them unset would freeze exactly the kind of default this function exists to leave out. A discriminator pins one value, so the rule counts them: measured across the spec, 31 single-value Literal fields, every one of them name or task, and the only two with more are those choices.

    Closes platypus#120. from_yaml’s docstring promised this round trip through as_dict(), a method no spec has ever had; it now names the function that exists.

  • available_losses(), available_metrics(), available_models(), available_optimizers(), available_callbacks() and available_tasks() - the rest of the verb available_transforms() and available_weights() already answered. The number of named components keeps growing, and the only way to see what is on offer was to leave for a documentation site.

An empty table would have been a third answer and the wrong one.

The four notes say what the code does differently - nested skips and the only architecture that can take deep_supervision, residual blocks, additive skips and the memory they save

[0.8.0a10] - 2026-10-11

Fixed

  • Four transforms were reported as unable to take a volume when what they could not take was the probe. available_transforms(rank=3) finds its answer by offering each transform a probe volume, and the probe was 8x8. A refusal is now retried once at 1024x1024 before it is believed, which is what Crop needs - its default crop box is 1024x1024, so no plausible small probe would ever have admitted it. The listing goes from 87 names to 91 on albumentations 2.0.8, and the four are Crop, FrequencyMasking, TimeMasking and Superpixels.

    Why two sizes rather than one bigger one, measured on one Linux machine, as a ratio because seconds are not portable: offering every transform the large probe takes 250x the 8x8 listing, while retrying only the refusals takes 8x. Most of that 8x is Superpixels, whose work scales with the pixel count. It is an lru_cached call made once per process, and a spec with no augmentation never makes it.

    The escalation can only add names - a transform that passed at 8x8 is never asked again - and a test takes the large size away and asserts Crop goes back to absent, because the straightforward test would pass for any reason at all, including an albumentations release that changed those defaults.

  • The 87-against-88 disagreement was never about the platform, and now has a mechanism. It had been recorded as “Windows with Python 3.13, and no mechanism is claimed”. The first version of the escalation test asserted that all four names were what escalation added, and ubuntu-latest with Python 3.10 reported three - which is how the real answer arrived:

    Superpixels at 8x8      4 of 60 attempts succeed; it samples `n_segments`, and
                        whether the segmentation divides by zero depends on the draw
eight listings, 8x8     87, 87, 87, 87, 87, 87, 88, 87 - one process, one machine
Superpixels at 1024     40 of 40 succeed
eight listings, now     91, eight times

    So the probe was a random variable and the matrix was reading its noise. The count is still not pinned anywhere, because stable on one machine is not portable - but it is no longer unexplained, and the test now asserts only what holds on every run: escalating never removes a name, never adds one outside the four, and always adds Crop.

    The three-channel nine are still refused, deliberately. That is a different decision, not an unfinished one: a three-channel probe would list ChromaticAberration and its eight relatives as available to someone whose CT has one channel, and a listing cannot know the channel count. Only the pipeline-build check can, and it already probes at the model’s own input size.

[0.8.0a2] - 2026-10-08

Added

  • cldice, a metric for structures where Dice asks the wrong question. Centerline Dice (Shit et al., CVPR 2021): each mask is scored against the other’s skeleton, so it measures whether a structure is connected rather than whether its pixels coincide. Vessels, airways, neurons, cracks, roads, catheters.

    The argument, measured here rather than quoted: a nine-pixel vessel drawn two pixels thin scores Dice 0.875, and the same vessel severed in the middle scores Dice 0.947 - Dice prefers the severed one. clDice gives them 1.000 and 0.943, which is the other way round. Its limit is measured too: at one pixel wide, a one-pixel displacement leaves no overlap at all and every overlap-based metric reads 0, this one included.

    The soft skeleton is iterated min and max pooling, which is differentiable, so the same function can serve a loss later; a hard skeleton would have been cheaper and not comparable with the paper. Rank-generic, and verified against scipy.ndimage’s own morphology - exact agreement, 2D and 3D, on random masks.

    Two silent failures are refused rather than scored:

    • a structure thicker than iterations can peel has an empty skeleton, and the ratios then read smooth/smooth. Measured: a 24-pixel square at iterations=1 gives clDice 1.0 to a prediction whose Dice is 0.0017. Refused by name;
    • include_background defaults to False here where every other metric defaults to True. The background’s skeleton lies inside the background by construction, so that class scores 1.0 whatever the model did - averaging it in moved 0.7865 to 0.8933 on a three-pixel vessel. Not a flattering average: a number with no meaning in it.

Changed

  • A tiled run refuses a whole-mask metric. splits hands the model pieces, and a skeleton is a property of a whole mask, so every structure would be severed at four tile edges and come back low for a model that is perfectly connected - silently. Refused when the specification is read, which is before anything is loaded. Dice is unaffected: its pieces sum, which is what combine exists for.

    What it is worth, and it is not what a table of scores shows. Three seeds, 60 epochs, lesions with ambiguous edges:

                 Dice             volume bias        |volume error|
plain        0.9639 ±0.0100   +1.71% ±12.18%     12.60% ±4.19%

[0.6.0a1] - 2026-10-06

A minor bump rather than another alpha letter: the data path grew a third item and the loss interface grew a flag, both of which a custom loss or loader would notice.

Added

  • boundary: a loss that knows how far a wrong voxel is from the truth. Dice and IoU count a voxel the same wherever it sits, which is why a model can reach 0.88 on Dice while its volumes run a fifth too large - the overshoot is all at the boundary, and for a small lesion the boundary is most of the object.

    loss:
  name: boundary
  region: {name: focal, gamma: 2.0}    # or dice, iou, tversky, ...
  alpha: 0.9

    mean(phi * p) added to a region loss, where phi is the signed distance to the truth’s boundary - negative inside, positive outside. Closes maju116/platypus#37, which asked for focal combined with a distance metric; region is how any of the nine is combined with it rather than one hard-coded pair.

    What it buys and costs, measured. Three seeds, 60 epochs, lesions with ambiguous edges, against Dice alone:

                     Dice             volume bias       volume |error|
dice alone       0.9525 ±0.0027   -5.18% ±3.11%     16.90% ±0.90%
boundary a=0.9   0.9411 ±0.0093   -0.06% ±4.15%     22.17% ±2.88%

    It trades accuracy per case for being unbiased over a series. “Is there a lesion” wants the overlap; “has it grown since March” wants a volume that is not systematically wrong, and no single number answers both. The bias improvement is suggestive on three seeds (the baseline’s own bias wanders ±3.11%); the costs are established.

    alpha defaults to 0.9, not 0.5, because 0.5 was measured and is unusable: at that weight the surface term has half the objective while the prediction is still random, and three seeds gave a volume error spread of ±28.28% with every number worse than the baseline. Kervadec schedules it downwards from near 1; 0.9 is the closest a single number comes.

Changed

  • The data path can carry a signed distance map, and the loss decides. A loss sets needs_distance, loss_needs_distance(spec) answers it from the specification, the loader computes the transform in its workers and the batch arrives with three items instead of two.

    In the loss it would have dominated training: one transform costs 5.3 ms at 256x256, 23.4 ms at 64x64x32 and 709.8 ms at 128^3, against an epoch of about half a second for a small 3D model. The paths that score or predict rather than optimise never call the loss, so they ask for two items and pay nothing.

  • scipy is a direct dependency. It was always installed, because albumentations requires it, but a package whose code imports scipy should say so rather than rely on somebody else’s dependency list not changing.

[0.5.0a6] - 2026-10-06

Added

  • crop_boxes() and DetectionEngine.crops(): every detection cut out of the image it was found in. The pipeline is a detector followed by a classifier it does not contain - find objects with three classes, crop them, hand the crops to something that knows eighty. predict returns boxes in each image’s own pixels precisely so they can be used on the photograph they came from; this is what uses them.

    for found in engine.crops("bccd", "test", size=(224, 224)):
    batch = np.stack(found["crops"])      # one shape, ready for a classifier

    Five decisions, each of which taken the other way quietly changes what a downstream model sees:

    • Cut from the source image, not the network input. DetectionDataset.source_image re-reads at native size through the same reader and the same options as read(), so a crop and a prediction cannot disagree about channels or the DICOM window. Cropping from the letterboxed frame would cut a downscaled object and then scale it back up.
    • Rounded outward, so the crop contains the whole box. Rounding to nearest loses up to a pixel per side, a twelfth of a 26-pixel platelet.
    • context expands by a fraction of the box’s own size, default 0, so one value suits a platelet and a white cell and nothing is expanded silently.
    • size letterboxes rather than stretches. Resizing a tall box to a square changes the aspect of every non-square object; fit="stretch" exists and must be asked for.
    • Always a list, even when size makes the shapes equal. A return type that depends on an argument makes every caller branch, and np.stack(crops) is the batch.

    crops() filters at operating_point rather than score_threshold, which is near zero so that average precision can integrate the whole ranking - cropping that would hand a classifier the tail AP exists to measure over.

    It also clips and drop_degenerates first, reporting dropped. That was found by the tests rather than reasoned about: a model may predict a box off the frame and predict reports what it said, so at a low threshold some arrive with no extent at all once the letterbox is undone. Still unreleased, and for the same reason as before rather than a new one. The §4f loop exists so the R package can reach a feature; R has no detection surface yet, so a release would serve nothing but the ceremony. It happens when the R side needs it.

Added

  • pyplatypus.detection, starting with metrics. The package this replaces had a YOLOv3 that trained and drew pictures and reported no precision, no recall and no average precision - its only number was mean IoU per grid, computed inside the loss, which measures agreement with the model’s own training target. So there was no way to say whether it detected anything, and no number to put beside published weights. Everything else is unmeasurable until this exists, which is why it is first

A detection number that disagrees with COCO is a number nobody can compare to anything

Added — detection in the specification

  • task, a discriminator on the specification: segmentation (the default) or detection. It selects the type of data and of every entry in models, rather than switching a flag, so a detection configuration carrying a colormap or a segmentation one carrying anchors is refused by name instead of silently ignored. One task per spec, not one per model, for the same reason there is one rank per spec: every model in a spec shares a data pipeline, and masks and boxes are not the same pipeline
  • A configuration with no task is a segmentation one, so every file and every released R package written before this keeps working unchanged
  • DetectionData - classes in class order (position is the class index, stated rather than read from the files, where it would come out alphabetical), annotation_format, coordinates for the VOC 1-based-inclusive convention, strict_labels. No background entry, unlike a colormap: a region of an image holding no object is not a box
  • DetectionModel - anchors as fractions of the input, fitted to the training data when unset; anchors_per_grid, ignore_threshold, score_threshold, nms_threshold, operating_point. Every one of these was a command-line flag in examples/detect_blood_cells.py, which is where a setting lives when it has nowhere better to be
  • DataSpec and ModelSpec, the shared bases the two tasks are built from. What they deliberately do not carry is loss and metrics: segmentation picks both from a menu of nine and three, YOLOv3’s objective is part of its architecture, and mean average precision is not one option among several. A field that accepts a value and ignores it is worse than no field
  • Refusals that cost nothing now and a confusing failure later: detection at rank 3 (ImageNet is images and YOLOv3 is a 2D architecture), an input side that is not a multiple of 32, anchors given in pixels rather than fractions - with the conversion named, since COCO publishes its nine in pixels at 416 - anchors that disagree with anchors_per_grid, grids with different anchor counts, duplicate class names, and coordinates set for LabelMe, which stores continuous pixel coordinates and has no convention to pick

Added — detection in the engine

  • bccd-yolo3 in the weights registry: YOLOv3 at 416x416 for RBC, WBC and Platelets, trained on BCCD (MIT) using the dataset’s own split, pinned to commit 24fbff08. mAP@0.5 0.857 on the 72 held-out images - the median of five seeds, not the best, because the spread is 0.0159 and reporting one run would be reporting whichever seed was chosen. The card states what decides whether the weights answer someone’s question: platelets are the unreliable class, precision 0.54 at confidence 0.5 and four times the seed-to-seed variance of the other two.

Two classes rather than one with a branch in every method: past discovery the two tasks differ at every step - three target tensors instead of one, a loss that is part of the architecture, and an evaluation that cannot be accumulated per batch because average precision is a property of a whole split’s ranking

  • DetectionDataset - one sample to one example, through the letterbox and the target encoder. One sample is one example, with no tiling: cutting an image into a grid cuts boxes in half, and half a box is not a smaller object

  • DetectionTrainer, reporting the four parts of the loss separately for train and validation. A YOLOv3 total means nothing alone - cross-entropy against a soft target bottoms out at the target’s own entropy, so the coordinate term has a floor above zero that depends on the data. coordinates 5.93 / objectness 0.001 is the difference between a model that has learned what is where and one that has stalled, and the total cannot tell them apart

  • Anchors are fitted to the training annotations when the spec does not give them, and recorded on the run and in the weights sidecar. Not optional metadata: the same weights read with other anchors decode every box scaled by a fixed factor, with plausible boxes, plausible scores, wrong places, and nothing in any output to say so

  • The targets are surveyed before the first epoch, and a dataset the encoder loses more than 2% of warns. Two boxes of one shape whose centres land in one cell share a slot, so the second is never shown to the model and never counted as missed. Measured on BCCD at a 416 input: 3 boxes of 2804

  • evaluate() returns the detection columns - map_50, map_50_95, mean_matched_iou - and no overall precision or recall. Averaging those over classes needs a weighting and every weighting is a different claim: summed over BCCD’s 4155 red cells, 372 white and 361 platelets, a single precision is a statement about red cells wearing the costume of a statement about the model. They are in evaluate_classes(), per class

  • predict() returns a list, in each image’s own pixels. There is no array form - images differ in size and so does the number of boxes found in each - and a box in a letterboxed 416x416 frame cannot be drawn on the photograph it came from. The same decision as space="source" on the segmentation side, except that here there is no alternative

  • anchor_coverage(), asked of whichever split you like. The useful question is about a split the anchors were not fitted on: 0.92 on training and 0.70 on validation says the two hold different objects, and no training curve shows that

  • A test split without annotations can be predicted and refuses to be scored. Scoring it against empty truth would report zero, which is a different statement from “there is nothing to score against”

  • config_file mode reads an annotations column for a detection spec - the second slot is named after what labels an image, and write_splits(label_column=...) writes it

Added — a learning-rate schedule the specification can state

  • cosine_annealing, a callback decaying the rate from its initial value to min_lr along a cosine. No monitor: it is a function of how far through the run you are rather than of how the run is going, which is the difference from reduce_lr_on_plateau, and a run may legitimately want both.

    It exists because wiring detection into the engine found that the specification could not express the run that produced this package’s published detection number. The measured BCCD run decayed its rate; a spec could only hold it constant.

    What the schedule is actually worth was then measured, and it is less than the gap it was reached for: adding it moved BCCD’s test mAP@[.50:.95] from 0.4700 to 0.4761 and mAP@0.5 from 0.8479 to 0.8496. The first explanation of that gap was wrong, and the measurement refused it; the rest of it was augmentation, which the engine did not do at all - the entry below. Attributing a gap to the plausible cause is the mistake this project keeps catching, and this time it took two tries.

    Both of those runs are single draws, so part of +0.0061 is the schedule and part is the draw - and five seeds of the finished recipe later put the standard deviation of mAP@[.50:.95] at 0.0199, which is three times that difference. The schedule is kept because it is the recipe the measurement used and because the spec could not state it, not because its effect was established. DETECTION_RECON.md §12 has the account.

  • Checked against torch.optim.lr_scheduler.CosineAnnealingLR epoch for epoch, at four run lengths and two floors. “The rate goes down” is not the claim worth testing: if this were a schedule that merely resembled torch’s, comparing a run through the specification with the measured one would compare two experiments and blame the difference on the wrong thing.

  • Each parameter group decays from its own initial rate, so encoder_learning_rate is not flattened at the first epoch - which would have been invisible, since the history records one learning_rate, the first group’s.

  • TrainingState gained total_epochs. A schedule that is a function of progress needs the horizon, and nothing else in the state implies it: epoch counts up and stops wherever early stopping stops it.

Added — augmentation for boxes

  • BoxAugmenter and build_box_augmenter: a spec’s augmentation list now applies to a detection run, with the boxes following the pixels. albumentations again, declared the same way as for masks, so a detection spec and a segmentation spec name transforms identically
  • Every geometric transform in albumentations 2.0.8 moves boxes with the pixels, which was measured rather than assumed. A bright rectangle with the box labelling it, twenty seeded draws per transform, comparing the box that came back with the bounding box of the bright pixels in the output. Eight are exact to 0.00 px - the flips, RandomRotate90, Transpose, D4, a pure translation, the crops - and five land within 1.00 px: Affine with a rotation or a scale, Rotate, Perspective, GridDistortion. For those five the box bounds the warped corners while the pixels are what survived interpolation, so the test asserts the box still covers the object rather than equals its extent. A property of the library, so it lives in the tests where a version bump re-runs it
  • min_visibility on a detection model: how much of a box must survive a transform that removes part of the frame. A convention rather than a measurement, and the direction is what is defensible - a box keeping two pixels of a cell teaches the model that a two-pixel fragment is a whole cell, which produces false positives everywhere, while dropping a heavily truncated object only fails to teach it about that object. Pascal VOC marks such objects truncated for the same reason. Irrelevant unless a transform can lose part of the frame, which flips and rotations never do
  • Training is augmented and validation never is: measuring a model on distorted data measures the distortion

Fixed

  • A probe that failed for its own reasons. The check that names a transform which cannot handle boxes ran against a fixed 32x32 image, so RandomCrop(height=64, width=64) - a perfectly good transform - was refused with “crop size exceeds image dimensions”. A probe that fails for the wrong reason is indistinguishable from a real refusal, and this one reported the user’s transform as unsupported when it was the check that was too small. Both probes now run at the model’s own input size, which also keeps the refusal correct for a crop genuinely larger than the input.

    The 3D volume probe had the same defect and had had it since it was written: a fixed 4x8x8 volume refused any larger 3D crop. Found only because the box probe made the shape of the mistake obvious.

  • albumentations rejects bad parameters with a pydantic ValueError, not Python’s TypeError, so a misspelled argument escaped the handler that exists to name it and arrived as schema prose. Both are caught now

  • A decaying learning rate was invisible in the output. learning_rate was printed to four decimal places like every other quantity, so a cosine going from 1e-4 to 1e-8 read learning_rate=0.0000 from epoch 90 on, and a run with a schedule looked identical to one without. Found by watching a run and trying to confirm the rate was moving; no test would have asked

  • seed did nothing. The field has been on the specification since the first release, described as “set it if you want a reproducible run”, and no code read it - so in R, platypus_spec(seed = 1) made a promise and two runs of it disagreed. Both engines now seed random, numpy and torch at construction, which also seeds the generator DataLoader derives its workers’ seeds from, so augmentation in a worker process is reproducible too. Found while wiring detection in, where the anchors are fitted by k-means and the seed had to come from somewhere.

    Asserted by training twice and comparing, and - the half that makes the first half mean anything - by checking that two unseeded runs differ. Without that second test the first would pass on a package that ignores seed entirely, which is the state it was in.

    What it does not do is ask torch for deterministic algorithms: that makes some convolutions much slower and makes others raise, so the result would be a seed that sometimes refuses to run. Two runs at one seed on one machine agree; across machines or cuDNN versions they need not

Added — annotations, letterboxing and the target encoder

  • Letterbox, which scales by one factor and pads, replacing the plain resize the old package used. That resize stretched a 640x480 photograph; it was internally consistent, since boxes were normalised by the source dimensions, but the COCO weights were trained on letterboxed input so loading them onto stretched images is a silent mismatch. The transform is reversible and carries what it did, so a box predicted in the network’s space goes back onto the pixels it came from - the detection counterpart of predict(space="source"). Padding is grey rather than black: black is a legitimate pixel value in a radiograph

Added — a detector, and the first number anyone can compare

The first number in this package’s history that can be compared with anybody else’s - the old YOLOv3 reported mean IoU per grid from inside its loss and nothing else, which is why its Blood Cell Detection example ended on a picture.

The ceiling is localisation, and it is size-dependent exactly as geometry predicts. AP by threshold: white cells hold 0.789 at IoU 0.80 while platelets fall from 0.820 to 0.041. And the loss converged rather than stalled. It plateaus at 5.936 against a floor of 5.891, computed exactly on real batches: cross-entropy against a soft target bottoms out at the target’s own entropy, so the coordinate term cannot reach zero. Two runs agreed to 0.003 of mAP.

Added — anchors fitted to your own boxes

  • generate_anchors, fit_shapes, box_shapes and anchor_coverage. k-means over box shapes with IoU as the distance, k-means++ seeding, carried over from the old package - the piece of it with no equivalent anywhere in R
  • AnchorFit carries mean_iou, the quantity the fit maximises and the number that says whether these anchors describe this data. Comparing it across anchors_per_grid is how the count gets chosen instead of assumed; the old implementation printed a class table and drew a scatter plot as side effects and reported no number at all
  • anchor_coverage answers “are COCO’s anchors good enough for my data” in one number rather than a training run. On blood-cell-shaped boxes: 0.67 borrowed against 0.92 fitted
  • The whole pipeline is verified against COCO’s published anchors. Plant the nine as clusters of boxes, refit from nothing, and COCO’s anchors come back in COCO’s groups to within 1-3 pixels at 416 - which checks the seeding, the distance, the convergence and the grouping at once

Fixed, in work carried over rather than in released code

  • Anchors are grouped into scales by area, not by width. Verified against the one external reference there is: sorting the nine COCO anchors by area reproduces their published grouping exactly, and sorting by width - what the old code did - does not. It puts (30, 61) in the finest grid and (33, 23) in the middle one, swapping them

  • Box shapes are measured in the space the encoder uses. The old code divided a box by its source image, which equals the fraction of the network input only when the image is stretched to fill it. With letterboxing a square object in a 640x480 image is square after letterboxing and 33% taller than it is wide under source normalisation. For a dataset of one image size the distortion is uniform and the model compensates; it stops being harmless the moment sizes are mixed or COCO weights are loaded

  • Pascal VOC’s one-pixel convention. VOC stores 1-based inclusive indices, so pixels 1 to 10 are ten pixels wide and xmax - xmin is nine - leaving 81% of the true area, which on a fifteen-pixel platelet is not a rounding question. The minima have 1 subtracted, once, where the format is known. Choosing wrongly is caught rather than silent: a minimum of 0 cannot occur under a 1-based reading, so a file containing one is refused with the alternative named

  • An infinity in the old target encoding. It stored logit(centre - floor(centre)), and that fraction is zero whenever a box’s centre lands on a cell boundary. Measured on a 416 input at grid 13: 37 of 1200 integer-pixel boxes, so about one in thirty had a -inf target. The target now holds the offset itself and the loss applies the sigmoid, so nothing is inverted and nothing can be infinite

Decided, and said in the code rather than assumed

Two numbers both honestly called “mAP” can differ by points on identical predictions, so detection_report returns the conventions it used beside the score.

  • Boxes are continuous (xmin, ymin, xmax, ymax). Pascal VOC stores pixel indices and adds 1 per side, which raises a 10-pixel box’s IoU by 21%; that belongs in the annotation reader, not here
  • Matching is greedy by descending score, one truth each, so a duplicate box is a false positive - which is what makes non-maximum suppression worth doing
  • Predictions are pooled across images before AP, never averaged per image. The curve is one ranking over the dataset; a mean of per-image APs is dominated by images with one object. Same reason the segmentation metrics sum TP, FP and FN before applying their formula - a ratio of sums is not the mean of ratios
  • A class with no ground truth scores None, not zero, and is left out of the mean; classes_without_truth says which. Three interpolations are offered - all (VOC 2010+), 101 (COCO) and 11 (VOC 2007) - because papers quote all three
  • difficult objects are excluded when annotations carry the flag, as VOC’s own evaluation excludes them

[0.3.0a3]

2026-09-26

Added

  • target_spacing on the data section: resample every volume to a common voxel size, then centre-crop or pad to the model’s input_shape. Without it a volume is resized into the box, and that is only harmless when two scans cover the same extent. Clinical scans do not: 40 slices of 1 mm is 40 mm of patient and 40 slices of 2.5 mm is 100 mm, so resizing makes the same organ a different size in each and nothing in the data says so. Resampling fixes the millimetres per voxel - the quantity anatomy is measured in - and cropping or padding afterwards is what turns the varying shape into the one shape a network needs without stretching away what the resampling established
  • resample_to_spacing() and crop_or_pad(), centred, usable on their own
  • Measured on a 10 mm sphere: 4189 mm3 in theory, 4224 at 1 mm slices. The same sphere at 2.5 mm slices reads 1688 voxels against the fine scan’s 4224 - a 60% difference in what is physically one object - and 3760 after resampling, an 11% difference. The rest is honest: at 2.5 mm the caps were never measured, and resampling recovers no information an acquisition did not take

Fixed

  • Masks went down a different reading path from images. With target_spacing the image was resampled and cropped while a single-file mask was merely resized, so every label sat beside the anatomy it was labelling - a misalignment that trains quietly and shows up as a model that cannot learn. Both now go through one function, and a test asserts the mask covers the tissue rather than merely having the right shape

[0.3.0a2]

2026-09-26

Added

  • Reading a DICOM series: a folder of slices becomes one volume, which is how data leaves a hospital. Four decisions, each of which produces a volume that trains without complaint when taken wrongly:
    • order comes from ImagePositionPatient projected onto the slice normal. Not the filename, which sorts slice 10 before slice 2, and not InstanceNumber either, which need only be unique within a series and is not required to follow the anatomy - it is the documented fallback when there is no geometry at all, and Series.sorted_by says which was used
    • one series at a time. A folder out of an archive usually holds several - a scout, a reconstruction, a phase - and SeriesInstanceUID separates them. Stacking two interleaves two anatomies at two resolutions
    • one window for the whole series. Slices of one series can record different windows; honoured slice by slice they produce a brightness gradient the scanner never measured
    • canonical orientation, through the same path a NIfTI takes, so one CT read from DICOM and the same CT converted to NIfTI arrive identically oriented
  • describe_series() checks a series without reading a pixel, because checking a hundred cases should not cost a hundred gigabytes
  • Slice spacing is measured from the positions, never from SliceThickness - thickness is how thick a slice is, not how far apart they sit, and for an overlapping reconstruction using it puts every slice past the first in the wrong place
  • A gap in the positions is an error. A volume stacked over a gap does not lose a slice, it puts everything past the gap somewhere else, and no metric would show it. With too few slices for the median gap to mean anything the message says it cannot tell which gap is wrong instead of naming one by arithmetic accident
  • Series reading is wired into the pipeline two ways: a 3D model with several DICOM files in one sample, and a path to a series directory in a CSV

Changed

  • Several volumes per sample - one per modality, as BraTS ships - is refused with a message saying so, rather than the first one being read and three quarters of the data ignored

[0.3.0a1]

2026-09-26

Volumes. The spec, the model builder, the losses, the metrics and the tiling were already rank-generic - input_shape = [64, 64, 32] has validated and built a 3D U-Net since 0.2.0a1 - so what was missing was reading volumes, naming classes the way volumes do, and two refusals that existed to stop a half-working 3D run.

Added

  • NIfTI reading (read_volume, volume_spacing), dispatched from read_image so everything reads “whatever is at this path, the way training would”. Two corrections happen before anything looks at the array:
    • canonical orientation. A NIfTI stores an affine, not an array in a known order, and the same anatomy can arrive in any of 48 permutations and flips. Read two datasets naively and one has the patient’s left on the right; train on both and the model can learn which dataset a scan came from. Every volume is reoriented to closest-canonical RAS, and there is a test that two files describing the same anatomy through different affines come back byte-identical
    • a fixed intensity window, the same named windows the DICOM reader uses, so ‘lung’ means one thing across the package. auto falls back to the range present for NIfTI, which stores no window - stated rather than silent, since that is the one case where a bright outlier still rescales everything else
  • labels in the data section: masks as label maps rather than pictures, which is how every volume format stores them. Exactly one of colormap and labels - not both even when they agree, since two sources for the number of classes means one going stale, and not neither, since guessing it from the data would let a validation set with no tumour quietly train a model with one class fewer
  • 3D patch sampling, which is splits at rank 3 and the same code as the 2D grid
  • resize_volume(), through torch rather than scipy: one library fewer to conflict with

Changed

  • The data pipeline and the engine no longer refuse a 3D spec. Trained end to end on synthetic 64x64x32 CT volumes on a GTX 1070: 0.5s an epoch, per-case Dice, and predictions returned as whole volumes
  • dicom_window is now window, since NIfTI needs the same thing and the old name had become a lie. dicom_window is still accepted - a released R package sends it - and giving both is an error rather than a coin toss
  • A class-count mismatch names whichever of colormap or labels is in use, instead of always blaming the colormap
  • nibabel is a hard dependency. A medical imaging package that cannot open a .nii.gz is not one

Not done, on purpose

  • Resampling to isotropic spacing. Spacing is read and carried, because losing it would make resampling impossible later; applying it changes the voxel grid the model sees, which is a decision to take explicitly rather than inside a reader
  • Augmentation in 3D. albumentations ships 3D transforms through a different call signature; a 3D spec asking for augmentation is refused, not silently ignored
  • DICOM series to volume. Reading one DICOM slice works; assembling a directory of them into a volume needs sorting by geometry and a consistency check, and is its own piece of work

2026-09-26

Added

  • split_dataset() - split one directory into train/validation/test CSVs, keeping every group whole. group_by is a regular expression read against the sample key, and a group is whatever must not straddle the split: usually a patient, sometimes a study, a scanner or a site. Slices of one patient on both sides of a split is the most common way to report a segmentation score that means nothing, and it leaves no trace in the output.
